01  Executive Summary
VEXUS is an integrated Web3 platform combining Raffle discovery and participation, Community management, Premium Automation, Reputation, Professional Identity, and Hiring — within one unified product.
The platform is built around the Web App, Admin Dashboard, and unified Backend as the core launch components, while the Mobile App (Flutter) is implemented in the final phase while preserving the same business logic and single source of truth.
A user-facing web application built with React / TypeScript, serving as the primary MVP surface.
An administrative dashboard built with React / TypeScript as a standalone application.
A unified Backend platform (APIs and Services) powering all platform surfaces from the same Single Source of Truth.
A mobile application (iOS / Android) built with Flutter, planned for the final phase and not within the MVP scope.
This document converts everything discussed with the client — together with the previous SRS and the Alphabot platform analysis used as a behavioral reference — into one detailed product specification, structured for review and approval before implementation begins.

2.2 Design Principles (Product Principles)
These principles govern every subsequent design or architectural decision in this document:
P1 — Free Participation
Users can participate in free Raffles without any subscription. Premium is not required for basic participation.
P2 — Premium = Software Capabilities, Not a Better Winning Chance
Premium provides Automation / Notifications / Account Capabilities / Community Management and other software capabilities. Premium must not become a purchase of a higher winning chance within the same Raffle, as that is a fundamentally different model that must be avoided to preserve Provably Fair credibility.
P3 — Non-Custodial
The platform never stores Private Keys or Seed Phrases. Wallet Signature is not used for login; any wallet signature required is solely for verifying ownership of the NFT/Main Wallet.
P4 — Performance First
Raffle Entry does not rely on expensive synchronous verification. Target: queued entry ingestion, with an initial response time below 300ms at p95, and an initial launch target of at least 5,000 submissions per minute per Raffle.
P5 — Provably Fair
Winner selection must be independently verifiable by any external party. Sequence: server_seed_hash → freeze ledger → entries_hash → public entropy → reveal → draw_seed → winners.
P6 — Centralized Platform Rules
Every Community uses a centralized Rule Catalog managed by Vexus (Super Admin), rather than each Community maintaining a completely different rule system. This simplifies maintenance and trust across the platform.

After creating the account, the user can link external accounts and services for login, the feed, and execution of Raffle requirements according to the function of each integration:
Discord

Google
Whop

5.3 Multiple X Accounts
Confirmed
Users can link multiple X accounts within the same VEXUS account and switch between them when participating in Raffles and satisfying eligibility requirements. This allows participation to continue when one account becomes unavailable, with each account recorded as an independent external identity.
The data model must support a 1:N relationship between User and SocialAccounts for X accounts, with clear policies for rate limits, provider restrictions, and prevention of multi-account abuse. The same account may also be used in the feed context and in executing Raffle requirements when appropriate for the integration.
5.4 Wallet: Add Wallet and Main Wallet Verification
Add Wallet: users can add multiple wallets for Raffle participation, Winning Wallet management, and other general use cases. Main Wallet: the user may perform Connect Main Wallet / Message Signing only to verify ownership of the wallet associated with the project's NFT holdings, in order to unlock NFT Holder benefits. This mechanism is not used as general login and the platform never stores private keys.

08  Raffle Modes / Participation and State Machine
8.1 The Four Modes
Mode / Type
Mechanism and Classification
Random / Weighted Raffle
Weighted Random Draw — Core Draw Mode. Weights are determined only by Raffle configuration and its rules; Premium provides no hidden increase in winning probability.
FCFS
First Valid N Entrants — Core Participation Mode.
Application
Applications + Manual Approval — Non-random Participation Mode, used when selection is based on application review.
Wallet Collection
Collect Qualified Wallets — Non-random Collection Mode, and does not itself produce random winners.
8.2 Classification Principles and State Machine
Random / Weighted is the primary draw mode; FCFS is the immediate-entry mode; Application and Wallet Collection are non-random participation modes within the same Raffle Engine. State machine: draft → scheduled → active → ended → finalizing → finalized, with the option to transition to cancelled from any of the first three states.

27  Security Architecture
27.1 Fixed Principles from the Start
Wallet Signature: used only when required to verify ownership of the Main Wallet associated with NFT holdings. There is no general Wallet-based Login and no storage of private keys.
OAuth Tokens: stored encrypted via Secret Manager / KMS.
Raffle Entry: CAPTCHA → Rate Limit → Identity Dedup → Verification, then create the Entry Idempotently, using the user's linked X accounts to execute X requirements.
27.2 Additional Layers
Audit Logs are immutable for every sensitive action.
2FA is mandatory for admin accounts.
All tokens are encrypted (Token Encryption) and sessions are rotated (Session Rotation).
Rate Limiting at both user and IP level.
Anti-Sybil layers to prevent multiple fake accounts.
Circuit Breakers to protect external services (Discord/X/Blockchain RPC) from cascading failure.
Backup / Point-in-Time Recovery (PITR) for the database.

30  Acceptance Criteria
Before accepting each Phase as complete, the following minimum criteria must be satisfied:
Initial Raffle Entry response time below 300ms at p95, with capacity for at least 5,000 submissions/minute per Raffle.
Every winner draw result must be independently verifiable (Verify Fairness) without blind trust in the server.
Mobile/Web parity is not required for the MVP; when Mobile launches in Phase 3, core functions must remain consistent with Web from the same source of truth.
No code path may store a Private Key or Seed Phrase on the server, and Wallet Signature must not be used as general login.
Every sensitive admin action must be recorded in a non-deletable Audit Log.
Pass a Load Test simulating a Raffle scenario with at least hundreds of thousands of concurrent participants for one large project.
